# 舰队学院动态属性存档实验

## 2026-10-06 更正：文本调试存档错误，正常存档支持动态属性

**下文 2026-10-01 的“动态属性会破坏存档”结论撤回。** 当时没有将文本调试输出与玩家使用的二进制存档区分验证。初次更正完成验证方法修复；随后按维护者要求，正式训练已迁移为原单位动态加成，实施与验证见下节。

### 根因

检查本机 Rusted Warfare 1.15 的 Java 字节码：文本写入器 `gameFramework.j.aw` 继承二进制写入器 `gameFramework.j.as`，覆盖了整数、float 等写入方法，却没有覆盖 `a(double)`。继承来的方法访问未初始化的 `DataOutputStream`，在 `SourceFile:309` 抛出空指针。动态属性差异以 double 写入，因此可触发此错误；自定义资源数值也会触发同一个错误，并不局限于训练。

2026-10-06 使用 `debug.plainTextDebugSave(true)` 重现同一写入方法的空指针，当前地图首先在队伍自定义资源写入处失败。用 `false` 切回正常存档，动态属性可以保存。无需修改游戏程序或禁用玩家存档。旧实验的完整失败日志未保留，因此不声称还原了当时每一个调用条件，但其“动态属性不能保存”的判断已被正常存档往返实测否定。

另一个独立问题是本机覆盖同名存档可能报 `Failed to rename to final file`。验证脚本使用每次唯一的存档名称，避免将重命名失败误判为序列化失败。调试接口返回 `done` 仅表示脚本执行结束，不能证明保存成功。

### 已完成实测

新增 `tools/smoke_game_saves.py`，仅允许在仓库 `work/` 下的隔离游戏副本运行，临时动作在退出时恢复：

```text
uv run --locked python tools/smoke_game_saves.py --game-dir work/game-sandbox
```

- Twin Chokepoints 地图中的 8 艘护卫舰原地增加 100 生命上限与 0.1 火力倍率，使用单位标签防止重复加成。
- 明确关闭文本调试存档，保存正常二进制存档；解压读取属性差异记录，确认 8 艘仍为 `rsCorvette`，生命上限 750（原 650）、火力倍率 1.1、已应用标签均存在。
- 在已经运行的游戏中读回该存档，日志达到 `Save file load complete`，再运行 5 秒并再次保存；属性与标签保留，未重复叠加，也未发生之前从空白 UI 直接载入时的渲染异常。
- 通过记录：`work/save-smoke-90e2c342a9f2/stdout.log`、`stderr.log`；存档位于隔离游戏的 `saves/save-smoke-90e2c342a9f2-*.rwsave`。文本错误复现记录：`work/academy-text.stderr.log`。这些本地产物不提交。

**结论：为避免这个存档错误而转换成独立精锐舰型并非必要。** 上述最小实验证明动态属性的正常存读档可行，正式机制迁移另做了以下验证。

## 2026-10-06 正式训练迁移

20 种作战舰体（14 种基础型、五种 T2、悖论泰坦）分别使用固定的训练生命上限、火力倍率 1.1 和单位 flag 1。先按新旧生命上限之比调整当前生命，再设置上限，保留受损比例。动作只在完工标记已存在且本队有已完成训练的学院时触发；已经达到训练上限的已训练单位不再触发。训练不再执行 `convertTo`，不改舰船名称、队伍、配装或命令。

维护者随后确认每队只允许一座学院，学院被毁或拆除后撤销加成，并明确不需要旧存档兼容。当前建造锁统计 `rsFleetAcademy`（含未完工建筑），AI 同时设置 `maxGlobal: 1`。训练成果改为学院自身的 `rsFleetAcademyActive` 标签；舰船查找本队活跃学院，学院消失后按本型号基础上限恢复当前生命比例、火力倍率 1，并清除 flag。重建学院不会继承训练，必须重新研究。研究排队禁止重复。

实测发现升级动作默认清除单位标签，而升级并不重新发送完工事件，导致原来的完工标记丢失。巡洋舰、战列舰及泰坦的升级动作因此设置 `convertTo_keepCurrentTags: true`，T2 升级补入 `rsTier2`。训练 flag 和完工标记保留，目标舰体恢复基础动态属性后自动按目标上限重新训练。

- 隔离记录 `work/academy-production-581e56e5/`：20 类舰体先设为半血，随后触发学院的真实训练动作（实验缩短研究/升级排队时间），所有舰型保留身份、达到各自约 115% 上限、半血比例保持在 49.9%–50.1%。为了隔离血量比例，实验禁止测试舰体受伤、自动维修与自修；正式配置未改这些能力。
- 对训练前后及读档后正常二进制存档检查；六条升级链为三类巡洋舰 T2、两类战列舰 T2、泰坦→悖论泰坦，均保留训练，升级后再读档并保存通过。检查不以调试命令的 `done` 回复作为成功依据。
- 早期迁移曾验证旧精锐单位存读档；维护者随后明确不需要兼容，现已删除全部 20 个 `*Veteran*` 定义及生成工具。当前验收仅覆盖新机制。
- 初次迁移的 180 单位检查、三张地图载入、地图检查和完整配乐包构建通过；移除旧舰型后为 160 单位。最终存续机制验收记录见下文，上述回归不替代联机与移动端验收。

实验配置均在隔离游戏中临时写入并在退出时恢复，日志和存档留在被忽略的 `work/`。正式规范见 `specs/combat-balance.md` 与 `specs/content-roster.md`。

## 2026-10-01 原始记录（结论已更正）

> 2026-10-01；Rusted Warfare 1.15；隔离副本 `work/game-sandbox`

目标是验证舰队学院能否以 `setUnitStats` 给现役及新造舰船一次性的生命上限与火力加成，并在存档中保留结果。正式模组尚未接入该实现。

1. 隔离配置把护卫舰的训练动作设为自动触发，使用 `@memory`/`setUnitMemory` 记录已训练，再用 `setUnitStats` 提升属性。地图能载入，但 `root.saveGame` 报 `java.lang.NullPointerException`，调用栈经过 `game.units.custom.as.a` 与 `game.units.custom.j.a`。
2. 改用单位 `setFlag=1`/`hasFlag(id=1)` 记录已训练，保留动态属性加成，存档仍报同一空指针。
3. 移除 `setUnitStats` 而仅留单位 flag，存档成功；重新加入最小的 `setUnitStats: maxHp+=100`，同样报空指针。
4. 撤回实验配置，同一隔离地图再次成功保存，生成约 463 KiB 的正常存档。测试进程所需的重复存档文件先删除，避免游戏覆盖重命名失败混淆结论。

当时据此判断动态属性路径会破坏存档，转而验证独立的训练舰船变体及单位转换；该判断已由上面的 2026-10-06 实验更正。实验中的舰队学院原创源图保留在 `art/generated/fleet_academy-source.png`。

## 后续验证：独立精锐舰型

已用 `convertTo` 与独立 `rsVeteran` 舰型替代动态属性。原型将 8 艘护卫舰转换后，纯文本存档显示队伍仍为原队伍，满血上限为 748（650 的约 115%），保存不再发生上述空指针。正式配置覆盖 14 种作战舰船，精锐舰型继承对应配装、贴图与动作，只覆盖身份、船体上限及 `shootDamageMultiplier: 1.1`。

隔离地图将同队的 14 种正式作战舰船各放置一艘，并通过测试专用阵营选择动作赋予训练标签；普通二进制存档识别全部 14 种精锐舰型，原有四艘 AI 护卫舰也转为精锐型，未获标签的玩家侧四艘仍为普通型。读档日志确认 38 个对象的单位数据完成读取并达到 `Save file load complete`；随后本机隐藏测试窗口的 `EnableScissorRegion` 渲染空指针中断了进一步交互，因此“读档后完整继续游戏”仍未验收。测试专用阵营标签与地图只存在隔离副本，不在正式模组内。
